# Subscription Background Refresh Source Contract

`subscription-background-refresh-source-contract=active`

`networkcore-linux subscription refresh start` explicitly refreshes one saved HTTP(S) source. It requires `--catalog`, `--refresh-status`, `--snapshot`, `--source-id`, and `--confirm`; it has no default path or source scan. The fixed minimum interval is 300 seconds. Timeout and the 1 MiB response bound come from `CommandRemoteSubscriptionFetcher`.

The response is parsed and normalized before any write. Success atomically replaces only the selected saved source's runnable catalog content, preserves its HTTP(S) refresh location, and writes the explicit pre-refresh catalog snapshot. Failed fetch or parsing preserves the catalog, node selection, and runtime configuration while recording a redacted failure.

The explicit status contains `source_id`, `last_attempt`, `last_success`, `next_attempt`, `result`, `added_node_count`, `removed_node_count`, `changed_node_count`, `error_redacted`, and a stable redacted `error_code`; it never contains a URL, token, password, or node credential. `subscription refresh status` is read-only and `subscription refresh stop --confirm` is bounded and idempotently records `stopped`. A short-lived exclusive lock derived from the explicit status path rejects concurrent refresh of the same source while allowing the next scheduled attempt. This command does not restart a core, switch nodes, or modify system settings.

Windows GUI uses the same status vocabulary for its explicitly user-enabled hourly refresh of one saved HTTP(S) source. Its persisted desktop state records `last_attempt`, `last_successful_update`, `next_attempt`, `result`, node diff counts, and a stable `error_code`; user-facing error text is redacted. A process-local exclusive operation guard rejects overlapping manual, source-selection, and scheduled refreshes. Each refresh is a single timeout-bounded operation, preserves the previous generated config, selected node, and runtime configuration on failure, and never restarts the core or switches a node. Windows does not create a service scheduler, discover sources, or retry an individual failed attempt.

`subscription refresh schedule install` is the Linux-only explicit scheduling boundary. It requires absolute `--catalog`, `--refresh-status`, and `--snapshot` paths, `--source-id`, `--interval-seconds` (at least 300), a suffix-free `--unit-name`, and `--confirm`. It first writes a non-overwriting rendered service/timer plan snapshot derived from the explicit snapshot path, then renders a NetworkCore-owned system `Type=oneshot` service and matching persistent timer under `/etc/systemd/system`, performs `daemon-reload`, enables and starts that named timer, and verifies it with `is-active`. No installation, enabling, discovery, or path scan occurs by default.

The service invokes the existing one-shot refresh entrypoint with only safe escaped local paths, source ID, interval, and `--confirm`. Unit contents never include a subscription URL, password, token, or node credential. Repeating exactly the same installation is idempotent; an existing different unit, symlink, or incomplete pair is rejected rather than overwritten. `schedule status`, `schedule stop --confirm`, and `schedule uninstall --confirm` require the original explicit snapshot path to compare the named pair byte-for-byte with its plan snapshot; they do not scan paths. Stop affects only that timer and retains the refresh status record. Uninstall removes only the matching NetworkCore-owned service/timer pair before reloading systemd and also retains that record for diagnosis. None of these operations restart a core, switch a node, or modify a system proxy.
