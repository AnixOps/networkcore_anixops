# Panabit iWAN 协议规格（净室实现用）

状态：草案 v0.2（2026-10-26）。适用：`iwan` 出站（客户端，§3–§11）与 `iwan` 入站（服务端，§12）。

## 0. 本文档的用途与净室规则

iWAN 是 Panabit 的 SD-WAN 私有隧道协议，没有公开文档。本仓库是 Apache-2.0 内核，实现必须与来源不明或 GPL 的代码隔离：

1. 本文档只用自然语言、表格和常数描述**线上格式、状态机和算法**，不包含任何其他实现的源代码或逐行翻译。
2. 实现者**只读本文档**编写 Rust 代码，不打开 Ricky-Hao/iwand、Ricky-Hao 的 sing-box fork（GPLv3）或其他 iWAN 实现，也不反编译 Panabit 官方客户端。
3. 互通性以黑盒行为为准：CI 中在固定 commit 下载并构建 iwand 仓库自带的 Go 测试服务端 `iwand-server`，作为独立进程运行，不链接、不复制、不随产物分发（见 §10）。真实 Panabit 设备的互通结果在拿到测试账号后补进本文档。
4. 本文档发现与实测不符时，先改本文档再改代码。

## 1. 协议概览

- 传输：UDP，单个服务端 `IPv4:port`。参考实现只用 IPv4 套接字；服务端是否接受 IPv6 **[待实测]**。默认端口无约定，必须由配置给出（常见值 4567）。
- 形态：**三层隧道**（我们的内核把它包装成逐连接出站，见 §11）。数据面载荷就是一个完整的 IP 包（参考实现只见过 IPv4），没有 TCP/UDP 代理语义，也没有目标地址字段。服务端在握手时给客户端分配一个隧道 IPv4 地址和 DNS。
- 一次会话：客户端反复发 OPEN 直到收到 OPENACK（或 OPENREJ），之后双向发 DATA，并定时发 ECHOREQ 保活和测延迟，结束时发 CLOSE。

## 2. 通用约定

| 名称 | 含义 |
| --- | --- |
| u16be / u32be | 大端无符号整数 |
| token | 2 字节，服务端在 OPENACK 头部给出，客户端原样回填，**不解释其数值** |
| session_id | 4 字节，同上 |
| 签名 | `MD5(包头 8 字节 ‖ "mw")`，16 字节，见 §3.2 |
| XOR 密钥 | `MD5(username ‖ password)` 的前 8 字节，见 §6 |

username、password 都按配置中的原始字节（UTF-8）处理，不加结尾 0。

## 3. 包格式

### 3.1 包头（所有包都有，8 字节）

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 1 | 包类型（§3.3） |
| 1 | 1 | 标志字节：在 OPEN / OPENACK / DATA_ENC 中表示加密模式（0 或 1），其余类型填 0 |
| 2 | 2 | token |
| 4 | 4 | session_id |

### 3.2 签名

控制包（OPEN、OPENACK、OPENREJ、ECHOREQ、ECHORESP、CLOSE）在包头之后紧跟 16 字节签名，载荷从偏移 24 开始。

签名 = MD5(包头的 8 个字节，再拼接 ASCII 两字节 `m` `w`，即 0x6D 0x77)。

- 签名只覆盖包头，**不覆盖载荷**，也不含任何密钥。它只是格式校验，不提供认证（见 §9）。
- 接收方校验：长度不足 24 字节，或重新计算的签名不等，则丢弃。
- DATA、DATA_ENC、IPFRAG、SEGRT 没有签名。

### 3.3 包类型

| 值 | 名称 | 方向 | 签名 | 说明 |
| --- | --- | --- | --- | --- |
| 0x11 | OPENREJ | S→C | 有（客户端不校验） | 认证失败 |
| 0x12 | OPENACK | S→C | 有 | 认证成功，携带会话参数 |
| 0x13 | OPEN | C→S | 有 | 认证请求 |
| 0x14 | DATA | 双向 | 无 | 明文 IP 包 |
| 0x15 | ECHOREQ | C→S | 有 | 保活与测延迟 |
| 0x16 | ECHORESP | S→C | 有 | 回显 ECHOREQ 的载荷 |
| 0x17 | CLOSE | 双向 | 有 | 结束会话 |
| 0x18 | DATA_ENC | 双向 | 无 | XOR 混淆后的 IP 包 |
| 0x21 | IPFRAG | S→C | 无 | 服务端分片，§7 |
| 0x22 | IPFRAG（SR 内层） | S→C | 无 | 只出现在 SEGRT 内层，§8 |
| 0x27 | SEGRT | S→C | 无 | 段路由封装，§8 |

客户端收到未知类型的包直接丢弃，不刷新活跃时间。

### 3.4 TLV

OPEN 和 OPENACK 的载荷是 TLV 序列：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 1 | 类型 |
| 1 | 1 | **总长度**，包含这 2 字节头本身（所以值 ≥ 2，值长度 = 总长度 − 2） |
| 2 | 总长度 − 2 | 值 |

解析规则：剩余不足 2 字节，或总长度 < 2，或总长度超过剩余字节数，视为格式错误。客户端遇到格式错误时停止解析，已解析的字段保留（与参考客户端一致）；未知类型跳过。

## 4. 握手

### 4.1 OPEN（客户端→服务端）

包头：类型 0x13，标志字节 = 配置的加密模式（0 关，1 开），token 和 session_id 全 0。然后是签名，然后按下面顺序写 TLV：

| 顺序 | 类型 | 值 | 何时发送 |
| --- | --- | --- | --- |
| 1 | 3 | 客户端 MTU，u16be（TLV 总长 4） | 总是（真实 Panabit 对不带此 TLV 的 OPEN 不回应，S3） |
| 2 | 1 | username 原始字节（TLV 总长 = 长度 + 2） | 总是 |
| 3 | 2 | 加密后的口令，16 字节（TLV 总长 18），见 §4.2 | 总是 |
| 4 | 8 | 加密模式 1 字节（值 1）（TLV 总长 3） | 仅当加密模式开 |
| 5 | 0x0A | 管道号 u16be：`pipe_id | (pipe_idx << 15)`（TLV 总长 4） | 仅当 pipe_id 或 pipe_idx 非 0 |

约束：

- MTU 范围 46–1600，默认 1400。
- username 长度受 TLV 总长 1 字节限制，最长 253 字节；参考客户端实际只支持到 31 字节，超过 31 字节时服务端是否接受 **[待实测]**。
- pipe_id 范围 0–32767，pipe_idx 范围 0–1。管道号的语义（多线路选择）**[待实测]**，第一版按配置原样透传。
- 服务端端口从 UDP 源地址读取，OPEN 里没有端口字段。

### 4.2 口令加密

1. 密钥 = `MD5("mw" ‖ username)`，16 字节，作 AES-128 密钥。
2. 明文 = 口令原始字节，截断或用 0x00 右补齐到恰好 16 字节。口令超过 16 字节时只用前 16 字节（服务端是否也截断 **[待实测]**，配置层应对超长口令给出警告）。
3. 密文 = AES-128-ECB 加密这一个 16 字节块（无填充、无 IV）。

### 4.3 OPENACK（服务端→客户端）

- 只在等待认证状态处理，其他状态收到直接丢弃。
- 必须通过签名校验。
- 包头的 token 和 session_id 就是本会话的标识，之后客户端发出的每个包（DATA、ECHOREQ、CLOSE）都原样带上。
- 载荷 TLV：

| 类型 | 值 | 含义 |
| --- | --- | --- |
| 3 | u16be | 服务端 MTU |
| 4 | 4 字节 IPv4 | 分配给客户端的隧道地址（**必需**） |
| 5 | 4 字节 IPv4 | DNS0 |
| 6 | 8 字节 | DNS0 ‖ DNS1（值不足 8 字节时只取 DNS0） |
| 7 | 1 字节 | peer dup pkt 标志（服务端可能重复发包，语义 **[待实测]**；第一版只记录不处理） |
| 8 | 1 字节 | 服务端确认的加密模式。**数据面是否加密以此为准**，没有此 TLV 时视为 0 |

- 值长度不足各自要求的字段忽略该 TLV。
- 没有类型 4，或地址为 0.0.0.0：视为握手失败，继续等待（直到 §5 的认证超时）。
- 有效 MTU = 配置 MTU；若服务端 MTU ≥ 68 且小于配置 MTU，则取服务端 MTU。
- 参考客户端把隧道地址配成 /24 掩码，这是本地决定，不在线上。我们按 §11 处理。

### 4.4 OPENREJ（服务端→客户端）

包头和签名之后可以带一段 ASCII 原因文本（不是 TLV，没有长度前缀，到包尾或第一个 0x00 为止）。S2 原型不带原因；真实 Panabit 带（S3）：

| 原因 | 含义 | 客户端提示 |
| --- | --- | --- |
| `INVPASS` | 用户不存在、口令密文不符，或口令加密方式不对 | 认证被拒绝（权限错误） |
| `NO_FREEIP_INPOOL` | 认证已通过，但服务端地址池没有空闲地址 | 服务端地址池已满（地址不可用） |
| 无原因或其他 | 未知 | 认证被拒绝，附上原文 |

客户端只取可打印 ASCII，最多 64 字节。客户端在等待认证状态收到 OPENREJ 时（不校验签名）结束本次尝试，按 §5 重连。OPENREJ **不刷新**活跃时间。

## 5. 状态机与定时器

计时粒度 1 秒。状态：

| 状态 | 进入条件 | 行为 |
| --- | --- | --- |
| 解析中 | 服务端是域名，且尚未解析或刚重置 | 每秒尝试解析一次（只取 IPv4），成功进入"待认证" |
| 待认证 | 已有服务端地址 | 立刻发一次 OPEN，之后每 2 秒重发；自进入本状态（或最后一次收到被接受的包）起超过 6 秒仍未建立 → 重置 |
| 已建立 | 收到合法 OPENACK | 每 2 秒发一次 ECHOREQ；距最后一次收到被接受的包超过 15 秒 → 重置 |
| 已关闭 | 收到合法 CLOSE 或 OPENREJ | 下一个计时点重置 |

重置：若之前已建立，先发 CLOSE（§6.3）并通知上层隧道断开；关闭并重新创建 UDP 套接字（换源端口）；清空 token、session_id、隧道地址、DNS、服务端 MTU、加密模式、分片缓冲和延迟统计；服务端是域名时回到"解析中"重新解析，否则回到"待认证"。

"被接受的包"刷新活跃时间：DATA / DATA_ENC（已建立时）、合法 OPENACK、合法 ECHORESP、合法 CLOSE、IPFRAG、SEGRT。OPENREJ 和未知类型不刷新。

接收过滤：只处理源地址和源端口都等于当前服务端地址和端口的 UDP 包，其余丢弃。

延迟初值：cur = 0，min = 5 000 000 µs，max = 0。

## 6. 数据面

### 6.1 DATA / DATA_ENC（双向）

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 8 | 包头：类型 0x14（明文）或 0x18（XOR）；标志字节 0x14 时为 0，0x18 时为加密模式（1）；token；session_id |
| 8 | N | IP 包（0x18 时为 XOR 后的字节） |

- 发送：已建立且协商加密模式为 1 时用 0x18 并 XOR，否则用 0x14。未建立时丢弃从隧道读到的包。
- 接收：只看类型字节决定是否 XOR 还原，不校验 token / session_id（与参考客户端一致）。载荷为空的包丢弃。
- S2 的服务端会丢弃与协商模式不符的类型（已协商加密却发 0x14，或反之），所以发送端必须严格按协商结果选择类型。
- 单个 UDP 包最大按 2048 字节处理；超过有效 MTU 的 IP 包由上层（隧道接口 MTU）避免，客户端不做分片。

### 6.2 XOR

密钥 K = `MD5(username ‖ password)` 的前 8 字节（这里的 password 是完整原始口令，不截断到 16 字节 **[待实测]**）。对载荷第 i 个字节（i 从 0 开始，**每个包都从 0 重新开始**）：`b[i] ^= K[i mod 8]`。加解密是同一操作。

### 6.3 CLOSE（双向）

24 字节：包头（类型 0x17，标志 0，当前 token 和 session_id）+ 签名，无载荷。客户端在主动断开和重置时发送一次；收到合法 CLOSE（已建立状态）进入"已关闭"。

### 6.4 ECHOREQ / ECHORESP

ECHOREQ：包头（类型 0x15，标志 0，token，session_id）+ 签名 + 36 字节载荷，总长 60 字节：

| 载荷偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 8 | 发送时刻，单调时钟微秒，**小端** u64 |
| 8 | 4 | 当前延迟 µs，小端 u32 |
| 12 | 4 | 最小延迟 µs，小端 u32 |
| 16 | 4 | 最大延迟 µs，小端 u32 |
| 20 | 4 | 全 0 |
| 24 | 4 | ASCII `T` `D` `R` 和 0x00 |
| 28 | 4 | route magic，u32be，没有时填 0 |
| 32 | 4 | 全 0 |

说明：参考客户端在 x86 上用本机字节序写前 20 字节，因此是小端；S2 服务端把载荷原样回显，不解析。真实 Panabit 服务端是否解析延迟字段 **[待实测]**。

ECHORESP：包头（类型 0x16，token，session_id）+ 签名 + 原样回显的 ECHOREQ 载荷。客户端校验签名后，用载荷前 8 字节算 RTT = 现在 − 发送时刻，更新 cur / min / max，并作为节点延迟上报给上层。

## 7. IPFRAG（0x21，服务端→客户端）

服务端可能把大包分片发来。格式：

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 8 | 包头（类型 0x21） |
| 8 | 8 | 未知（参考实现称 id_lo，不使用） |
| 16 | 4 | 分片组 ID，作为不透明 4 字节比较 |
| 20 | 4 | 位域，**小端** u32：bit 0 = 最后一片标志；bit 2–14（13 位）= 分片偏移（字节）；bit 15–25（11 位）= 本片长度 |
| 24 | 本片长度 | 分片数据 |

- UDP 包总长必须恰好等于 24 + 本片长度，本片长度为 0 的丢弃。
- 重组：按分片组 ID 分槽，最多 10 个并发组，每组最多 4096 字节，5 秒内没有新分片则丢弃该组。参考实现对"非最后一片"的拼接顺序与"最后一片按偏移放置"不一致 **[待实测]**；第一版实现按偏移放置每一片，收到最后一片且 `[0, 偏移 + 长度)` 全部覆盖时完成。
- 重组完成后，若协商加密模式为 1，对整个包做 §6.2 的 XOR（这里由会话模式决定，不由类型字节决定），再交给隧道。
- 客户端从不发送 IPFRAG。

第一版要求：实现解析和重组，用单元测试覆盖；真实服务端何时会发 IPFRAG **[待实测]**。

## 8. SEGRT（0x27，段路由）—— 第一版不实现

参考实现描述的格式：包头之后 4 字节段路由头（下一跳序号、链路数 n、低 3 位加密算法 + 高 5 位填充长度、标志），随后 n × 4 字节链路 IPv4，再后面是一个完整的内层 iWAN 包（DATA、DATA_ENC 或 0x22 分片），可能整体经 AES 加密。参考实现自己注明其 AES 密钥派生是"简化"版本 **[S1 推测]**，不能作为实现依据。

第一版行为：收到 SEGRT 时，若段路由头声明的加密算法为 0（不加密），且内层是 DATA 或 DATA_ENC，则按 §6.1 处理内层；其他情况丢弃并计数。配置项 `srlinks`、`srpassword`、`srencryptmode` 不支持，导入时提示忽略。

## 9. 安全性评估（必须在 UI 和文档中说明）

iWAN 的"加密"不提供保密性或认证：

- XOR 密钥只有 8 字节且每个包重复使用；IPv4 头前 8 字节大多可预测，一个包就能还原密钥。等同明文。
- 签名不含密钥，只覆盖包头，任何人都能伪造控制包；看到 token 和 session_id 的人可以伪造 CLOSE 断开会话，或注入 DATA（客户端不校验 DATA 的会话字段）。
- 口令密文是确定性的（同一用户名和口令每次相同），截获一次 OPEN 即可重放登录。

结论：iWAN 只适合接入用户自己已有的 Panabit SD-WAN 内网，或叠加在其他加密隧道之上。客户端 UI 在节点详情里标注"该协议不加密"。

### 10.1 测试服务端 `iwand-server` 的运行事实（来自 S2，仅用于搭建 CI）

构建：

- Go 模块路径 `github.com/Ricky-Hao/iwand`，go.mod 声明 `go 1.22`，只用标准库，无第三方依赖。
- 在仓库根目录：`CGO_ENABLED=0 go build -trimpath -o iwand-server ./cmd/iwand-server`。不需要 CGO，不需要 build tag。其上游 CI 也是这样构建的（`actions/setup-go` 读 go.mod 的版本）。

运行：

- 唯一参数 `-config <JSON 文件路径>`（必需）。没有日志级别参数；日志写到 stderr，前缀 `iwand-server: `，启动时打印监听地址，之后只在处理出错时打印。SIGINT / SIGTERM 退出。
- 无出口模式（默认）只开一个 UDP 套接字，**不需要 root、CAP_NET_ADMIN 或 TUN 设备**。出口模式才需要，CI 不开。

配置（单个 JSON 对象，**拒绝未知字段**）：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `listen` | 字符串 `host:port` | `127.0.0.1:4567` | UDP 监听地址。启动时 stderr 打印一行 `listening on <实际地址>`，所以也可以用 `127.0.0.1:0` 再从这行读出端口 |
| `mtu` | 整数 | 1400 | 46–1600；OPENACK 下发 min(此值, 客户端 MTU) |
| `dns` | 字符串数组 | 空 | 0–2 个 IPv4；1 个时下发 TLV 5，2 个时下发 TLV 6，0 个时不下发 DNS |
| `users` | 数组 | 必需，至少 1 个 | 每项 `username`、`password`（都必需、非空）、`address`（必需，非 0 的 IPv4，用户间不能重复，就是 OPENACK 下发的隧道地址，没有地址池）、`allow_encrypt`（bool，**默认 true**） |
| `exit` | 对象 | `enabled: false` | 省略即为无出口模式 |

示例（两个用户，一个禁止加密）：

```json
{
  "listen": "127.0.0.1:45670",
  "mtu": 1400,
  "dns": ["1.1.1.1", "8.8.8.8"],
  "users": [
    {"username": "plain", "password": "pw-plain", "address": "10.20.30.10", "allow_encrypt": false},
    {"username": "xor", "password": "pw-xor", "address": "10.20.30.11"}
  ]
}
```

行为：

- 加密协商：OPEN 标志字节非 0 **或** TLV 8 值非 0 表示客户端请求加密；最终加密 = 请求加密且该用户 `allow_encrypt`。OPENACK 头部标志字节和 TLV 8 都给出最终结果（总是带 TLV 8）。token 和 session_id 每次随机生成。
- 认证失败（用户不存在、口令不符、签名错、TLV 格式错、缺用户名或口令 TLV、MTU 越界）一律回 OPENREJ（只有签名过的 24 字节头，token / session_id 为 0）。
- XOR 密钥用完整口令计算；口令 TLV 按完整口令截断/补齐到 16 字节后加密比对。
- 同一 UDP 源地址或同一用户名再次 OPEN 成功时，旧会话被替换。会话按（UDP 源地址、token、session_id）三元组查找。
- DATA / DATA_ENC 的处理（无出口模式）：
  - 找不到会话（包括 CLOSE 之后）：**静默丢弃**，不回 CLOSE 也不回 OPENREJ。ECHOREQ 同理。
  - 类型与协商结果不符（已协商加密却发 0x14，或反之）：静默丢弃。
  - 载荷是合法 IPv4 包且目的地址等于某个**已连接用户**的 `address`：转发给那个用户（用该用户自己的 token、session_id 和加密模式重新封装）。目的地址就是发送者自己时，等于回给发送者。
  - 其他情况（目的地址不属于任何已连接用户，或载荷不是 IPv4）：把**收到的原始载荷字节**回给发送者。
  - 回送 / 转发都不修改 IP 包：不交换源/目的地址，不重算校验和（无出口模式不按 IPv4 总长度截断）。
  - 回送时按接收方会话的协商结果封装：加密会话用 0x18（标志字节 1）并 XOR，否则用 0x14（标志字节 0）。
- CI 建议：回显测试的目的地址用不属于任何用户的地址（如 192.0.2.1），期望收到逐字节相同的包；转发测试让两个客户端同时在线，A 发往 B 的 `address`，B 应收到。
- ECHOREQ：校验签名并找到会话后，把载荷原样放进 ECHORESP 回给该会话。
- CLOSE：校验签名后移除会话，不回包。

### 10.2 测试客户端 `iwand` 的运行事实（来自 S1 9f6a0e3，仅用于搭建 CI）

只用于在 runner 上把参考客户端当黑盒拉起来，对我们的 `inbound-iwan` 做第三方互通。只构建和运行，不链接、不分发。

- **构建**：C 程序，不是 Go。在仓库根目录执行 `make`，得到 `./iwand`。只需要 `cc` 和 libc，没有其他依赖，也不涉及 CGO。`make static` 构建静态版。仓库里的 Go 代码（`cmd/`、`server/`）是 §10.1 的服务端，和客户端无关。
- **命令行**：`iwand -f <配置文件> [-l <日志文件>] [-F]`。
  - `-F` 前台运行。不加时会 daemonize 并 chdir 到 `/`，CI 必须加 `-F`。
  - 不给 `-l` 时日志写到 stderr，每行以本地时间 `YYYY-MM-DD HH:MM:SS ` 开头。
  - 默认配置路径 `/etc/iwan/iwan.conf`。
  - 退出：SIGINT / SIGTERM 退出，SIGUSR1 触发重连。
- **配置文件**：INI 风格。`[名字]` 一节给出 TUN 接口名，然后是 `key=value`，`#` 开头为注释：

  ```
  [iwan0]
  server=127.0.0.1
  port=4567
  username=plain
  password=pw-plain
  mtu=1400
  encrypt=0
  ```

  `#` 只在行首才是注释，**不支持行尾注释**（会成为值的一部分）。`server` 可以是 IPv4 或主机名；`port` 必填，没有默认值；`password` 超过 16 字节会截断并警告；`mtu` 范围 46–1600；`encrypt=1` 请求 XOR。可选 `up_script=` / `down_script=`，用 execv 调用。

  两个脚本的参数依次为：事件（`up` / `down`）、TUN 名、地址、MTU、DNS0、DNS1。
- **TUN 与路由**：
  - 启动时自己打开 `/dev/net/tun` 创建 TUN（`IFF_TUN | IFF_NO_PI`）。
  - 收到 OPENACK 后，把下发地址以**固定的 /24 掩码**设到 TUN 上，拉起接口，设置有效 MTU。所以内核只会有该 /24 的直连路由。
  - **不加默认路由，也不加其他路由，不修改 `/etc/resolv.conf`**。需要的路由和 DNS 由 CI 自己用 `ip route` 配置，或者交给 `up_script`。
  - 隧道 DNS 的地址只出现在日志和 `up_script` 的参数里。
- **权限**：需要 root 或 CAP_NET_ADMIN（创建 TUN、ioctl 设地址、MTU 和 UP）。
- **可等待的日志字样**：
  - 启动成功：`SD-WAN client started successfully`。
  - 每次发 OPEN：`sending OPEN (N bytes)`。
  - 认证成功：`ESTABLISHED: ip=<地址> mtu=<MTU> encrypt=<Y|N> session=<token>`。
  - 被拒：`peer AUTH REJECTED`，之后在下一个计时点重置并无限重试，不会退出。
  - 等不到回应：`AUTH timeout`。
  - 配置错误时打印 `config error: ...`，退出码 1。
- **退出清理**：若处于已建立状态，会发 CLOSE（日志 `sent CLOSE to server`）并调用 `down_script`。之后关闭 socket 和 TUN fd；TUN 随进程消失，路由随之消失。

## 11. 内核集成（本仓库架构约定，非协议内容）

用户要求 iWAN 节点能像普通代理节点一样参与分流（2026-10-26），所以 iWAN 做成**逐连接出站**，不做整隧道模式。

- 新 crate `crates/outbound-iwan`，分两层：
  - 无 I/O 的编解码和客户端状态机（§3–§8），便于单元测试；
  - 出站适配：实现 `engine_outbound::TcpOutbound`（`connect` 和 `open_udp`），类型名 `iwan`，在 `engine_outbound` 注册表和 `engine-embedded` 的 `protocols.rs` 表中登记；`engine-embedded` 增加 cargo feature `iwan`（默认开启）。
- 每个 iWAN 节点实例持有：一个 UDP 会话（§5 状态机，惰性建立：第一条连接到来时握手，空闲一段时间后可发 CLOSE 释放）和一个**节点私有的用户态 TCP/IP 栈**（smoltcp；仓库已经通过 `netstack-smoltcp` 依赖它）。栈的本机地址 = OPENACK 下发的隧道地址，MTU = 有效 MTU，默认路由指向隧道。
- `connect(target)`：在私有栈里主动发起 TCP 连接，返回的流即为 `BoxStream`。`open_udp(target)`：在私有栈里绑定一个临时 UDP 端口，收发数据报。栈输出的 IP 包按 §6 封装成 DATA / DATA_ENC 发出；收到的 DATA、IPFRAG 重组结果交给栈。
- 目标是域名时，通过私有栈（UDP 53）解析：配置了 `dns` 就始终用配置值（覆盖下发的 DNS），否则用 OPENACK 下发的 DNS；都没有则报错。分配的地址和 DNS 只在节点内部使用，**不修改平台的网络设置**。
- 会话惰性建立：没有任何连接满 60 秒后发 CLOSE 释放会话。
- 重连（§5 重置）后，若分配的隧道地址和有效 MTU 都没变，保留私有栈和现有连接；否则换新栈，已有连接全部以错误结束（上层按普通断线处理）。
- 多个 iWAN 节点互相独立，可以和其他协议的节点一起放进策略组，按规则、手动选择或测速选择。节点测速可直接用 §6.4 的 ECHO RTT。
- 资源：iOS Network Extension 内存很紧，私有栈的 TCP 收发缓冲区要设上限（`tcp_buffer_bytes`，默认每连接每方向 64 KiB），且只在有连接时创建栈。
- 不支持的流量：ICMP（ping）等非 TCP/UDP 流量不经过逐连接出站，因此不会走 iWAN 节点。
- 配置字段：`server`（域名或 IPv4）、`port`、`username`、`password`（由 Keychain 注入，与其他协议一致）、`mtu`（默认 1400，46–1600）、`encrypt`（bool，默认 false）、`pipe_id`（默认 0）、`pipe_idx`（默认 0）、`dns`（可选，最多 2 个 IPv4，设置后覆盖下发的 DNS）、`tcp_buffer_bytes`（可选，每连接每方向的 TCP 缓冲，默认 65536，范围 4096–1048576）。
- 节点导入（anixops-net）和 UI 在内核合并后另行进行。

## 12. 服务端（`inbound-iwan`，节点内核 anixcore）

用途：让 iwand、OpenWrt 路由器、Panabit 设备等 iWAN 客户端接入我们的节点，再由面板的域名分流（anix-control「转发 → 分流」，Agent 下发的 `egress` 成员）决定出口。本节是对客户端行为（§3–§7）的服务端对应，实现仍然只读本文档。

### 12.1 会话

- 一个 UDP 监听端口服务所有用户。会话按（客户端 UDP 源地址、token、session_id）三元组查找。
- OPEN 处理：校验签名和 TLV（§3.4，服务端遇到格式错误整包拒绝）；必须有用户名 TLV、长度恰为 16 的口令 TLV；客户端 MTU 缺省按 1400，范围 46–1600。用户不存在、口令密文不符（按 §4.2 用该用户的口令算出密文后**常数时间比较**）或任何格式错误，一律回 OPENREJ：包头类型 0x11、其余为 0，加签名，后接原因 `INVPASS`；地址池耗尽时原因为 `NO_FREEIP_INPOOL`（§4.4）。缺 MTU TLV 时按 1400 处理而不是像真实 Panabit 那样不回应：宽松处理没有代价，已知客户端都会发这个 TLV。
- 成功：token（2 字节）和 session_id（4 字节）用安全随机数生成；有效 MTU = min(节点 MTU, 客户端 MTU)；加密模式 = 客户端请求加密（标志字节非 0 或 TLV 8 非 0）且入站允许加密（入站级 `allow_encrypt`，默认 true，不按用户区分）。回 OPENACK：包头类型 0x12，标志字节为加密模式，带新的 token 和 session_id，加签名，TLV 依次为 3（有效 MTU）、4（分配的隧道地址）、5 或 6（DNS，见 §12.3）、8（加密模式，总是发送）。
- 同一用户名或同一 UDP 源地址再次认证成功时，旧会话立即移除（客户端换端口重连是常态，见 §5 的重置）。
- 客户端在等待期间每 2 秒重发 OPEN：同一源地址在会话建立后又发来 OPEN，按新认证处理（替换旧会话），不要回复旧的 OPENACK。
- ECHOREQ：校验签名并找到会话后，回 ECHORESP（包头类型 0x16、该会话的 token 和 session_id、签名、原样回显载荷）。
- CLOSE：校验签名，找到会话则移除，不回包。
- 空闲超时：会话 60 秒内没有收到任何被接受的包（客户端每 2 秒发 ECHO，§5）则移除。
- 找不到会话的 DATA / ECHOREQ 静默丢弃；类型与协商加密模式不符的 DATA 静默丢弃。
- 不实现 IPFRAG 和 SEGRT 的发送；服务端发出的 IP 包不超过该会话的有效 MTU：TCP 由用户态协议栈的 MSS 保证，超过 MTU 的其他包按普通 IPv4 分片发出（不用 IPFRAG）。

### 12.2 地址池

- 每个 iWAN 入站配置一个 IPv4 网段（例如 `10.66.0.0/16`）。网段第一个可用地址留给节点自己（隧道网关，也是 DNS 地址），其余按用户分配。
- 同一用户重连时尽量拿回上次的地址（按用户 id 记住最近一次分配），地址回收在会话移除 10 分钟后。
- 面板可以给用户指定固定地址（可选），与池内动态地址不冲突。
- 每个会话只接受源地址等于分配地址的 IPv4 包（防伪造），其余丢弃并计数。

### 12.3 从三层包到连接，以及域名分流

- 每个入站一个用户态 TCP/IP 栈（smoltcp），以"任意目的地址都接受"的方式终结会话发来的 TCP 和 UDP（与 iOS 隧道里的 netstack 用法相同）。每条终结出来的连接都带着所属用户，交给节点的路由和出站，流量记到该用户。
- 节点对隧道内提供 DNS：网关地址的 UDP 53。OPENACK 下发的 DNS 就是这个网关地址（TLV 5）。节点 DNS 用上游解析器解析，并记录"解析结果 IP → 域名"的映射（按 TTL 过期）；之后到这个 IP 的连接就带上域名，面板的域名分流规则据此选出口。
- 兜底：TCP 首包的 TLS SNI / HTTP Host 嗅探出的域名优先于 DNS 映射。两者都没有时只按 IP 路由。
- ICMP：只回应发给网关地址的 echo 请求（便于客户端判断隧道通断），其他 ICMP 丢弃。
- 客户端之间互访（目的地址是另一个在线用户的分配地址）默认禁止，可在入站配置里打开。

### 12.4 节点与面板集成（本仓库及 anix-agent / anix-control 的约定）

- anixcore 新增入站类型 `iwan`，配置：`listen`、`mtu`（默认 1400，范围 576–1600，因为它决定 TCP MSS）、`pool`（IPv4 网段）、`dns_upstream`（`ip` 或 `ip:port`，默认 `1.1.1.1:53`）、`allow_encrypt`（默认 true）、`allow_client_to_client`（默认 false）。
- 用户由 Agent 通过管理 API 增删。engine-inbound 的通用用户增加两个可选字段：`username`（iWAN 登录名，缺省用 `name`，即面板用户 id）和 `address`（固定隧道地址）。口令最长 16 字节（§4.2）。登录名和固定地址在同一入站内必须唯一：管理 API 增加用户时遇到重复应拒绝该用户并报错，不能静默覆盖（否则流量会记到错误的用户）。
- anixcore 实现面板 `egress` 成员（域名列表 → SS-2022 中继到出口节点），对 iWAN 入站和其他入站一样生效。
- anix-agent：面板 iwan 节点映射到 anixcore 的 `iwan` 入站；anix-control：节点类型增加 iwan，用户页显示 iWAN 登录名、口令和分配地址；iWAN 没有订阅格式，客户端手工填写。
